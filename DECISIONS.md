# DECISIONS

Where `spacerocker-prompt.md` was ambiguous, or where the reality of the machine
and the libraries forced a detour, the choice is recorded here — with the why.
The spec remains the source of truth; this is the errata.

---

## Environment

### 1. Python was installed on this machine

The machine had no Python — only the Microsoft Store stub. The sprite pipeline in
§9 is Python + Pillow, and the Act I atlases that shipped with the package were
generated by it, so porting the generator to another language would mean Act II
and Act III art that looks different from Act I — exactly what §9 forbids in its
*fallback* paragraph.

Installed: Python 3.12.10 (user scope, via winget) + Pillow 12.3.0 + numpy 2.5.3.

**Verification:** with that toolchain, `python -m spritegen.build --act 1`
reproduces `act1_*` and `boss_hexapod_*` **byte for byte** against the files that
came in the package. The pixels are identical; only the PNG zlib stream differs
between Pillow versions, and the package was regenerated with the local Pillow so
the repo stays coherent.

### 2. React pinned to 19.2.x

`@react-three/fiber@9.7` declares `react@">=19 <19.3"`. With `react@^19.0.0`, npm
resolved 19.3 and the install failed. Pinned to `~19.2.8`.

## Sprite pipeline

### 3. Generator output goes to `public/sprites/`

It was `out/sprites/`. Vite serves `public/` directly, so pointing the generator
there removes a manual copy step between generating and playing.

### 4. JSON written explicitly with LF

`Path.write_text` uses the platform's text mode; on Windows that produced CRLF,
and the same code emitted different bytes per operating system. That broke §15's
"reproduces bit for bit" criterion outside Linux. Now `newline="\n"` in
`atlas.py` and `build.py`.

### 5. `build_hexapod` became a generic `build_boss`

The three bosses share a single builder; the Hexapod's metadata moved out of
`build.py` into `hexapod.py` (`META`/`PHASES`/`GUNS`), matching the other two.
Refactor verified: the Hexapod atlas is still byte-for-byte identical.

### 6. Each act's atlas holds only that act's cast

`act1` keeps the original 4 (preserving the shipped bytes); `act2` has 8 and
`act3` has 11. The hull does not change between acts — only the emissive — so
each atlas re-renders the list that act actually uses (`ACT_SHIPS` in
`enemies.py`).

### 7. The contact sheet links the PNGs instead of embedding them

With 6 atlases, `inline` mode produced a 19 MB HTML file. The page now lives next
to the PNGs in `public/sprites/`, so it does not need to embed them. It is still
the review screen §9 requires.

## Engine

### 8. `@react-three/drei` was not included

Every GPU resource is created and updated imperatively, outside React. Drei's
helpers are declarative and would only pay off in a JSX scene graph — which is
exactly what §4 forbids during play. No unused dependencies.

### 9. `postprocessing` used directly, not `@react-three/postprocessing`

The React wrapper exists only to declare effects in JSX. The composer is driven
by the same frame callback that runs the fixed step, so the base library is used
directly. Same library, without the declarative layer.

### 10. `mipmapBlur` disabled on SelectiveBloom

With `mipmapBlur: true` plus a half-float buffer, the pass **wiped the entire base
image** — a black screen with only the glow left. Reproduced by isolating effect
by effect and measuring mean frame brightness: no bloom 5.09, with bloom 1.78,
with `mipmapBlur: false` 6.94. It is a mipmap-generation limitation on float
textures under software GL (and unstable on some integrated drivers — precisely
§12's performance target). Uses `KernelSize.LARGE`; the result is practically
indistinguishable.

### 11. Gameplay layers do not depth-test

Sprites, projectiles and particles use `depthTest: false` plus an explicit
`renderOrder`. With depth testing on, the terrain swallowed the billboards (the
ship vanished behind the ground it was flying over). Ordering is fully determined
by layer and insertion order — including boss parts, which stack hull →
peripherals → core. This matches §3's rule: if an effect hurts readability, the
effect goes.

### 12. AI behaviours in a single file

§13 asks for "one file per behaviour". All 11 live in `src/game/ai/index.ts`,
separated by header: each is ~25 lines and they all share the weapon/telegraph
helpers (`tickWeapon`, `aimAt`, `avoidWalls`). Eleven 25-line files with the same
3 imports would be worse to navigate, not better.

### 13. Projectiles and particles outside miniplex

Miniplex holds ships, pickups and boss parts (dozens of them). Projectiles (1200)
and particles (2000) live in struct-of-arrays pools of typed arrays. That is what
makes the fixed step allocation-free, as §4 demands, and the spec itself already
calls for projectiles to be a pool plus an `InstancedMesh`.

## Gameplay (adjustments made by playing)

### 14. Enemies no longer inherit the full scroll speed

Adding `scrollSpeed` to an enemy's own speed gave ~24 u/s: they crossed the
visible area in 1.3s and were impossible to fight. Each enemy now uses its own
speed; only the `turret`, which is anchored to the terrain, rides the scroll.

### 15. Bosses drop an energy cell every 13s

The pickup table only covers the wave phase, but energy keeps draining during the
fight. In a long boss fight the player died of fuel, not of the boss. A test that
counted cells per level exposed it.

### 16. `entryZ` and `cameraPull` per boss

§8 says the camera pulls back 40% for the Ouroboros. That was missing: without
it, the boss covered the whole screen and left no lane to dodge in. Each boss now
declares where it parks (`entryZ`) and how much it pulls the camera
(`cameraPull`).

### 17. A missing boss atlas ends the level instead of hanging

`maybeSpawnBoss` retried every step when the atlas did not exist, and the level
never finished. It now ends the level, so a run stays playable even if an atlas
is missing.

## Player requests (after the first version)

### 18. Camera pulled back: `CAM_DIST` 19 → 25 *(superseded by 26)*

The field of view was far too tight for the genre. At 19 the visible area was
~16 units deep, and an enemy at 6–15 u/s stayed visible for 1.3–2.5s — too short
a reaction window. At 25 it is ~21 units (+31%), and the corridor fills ~56% of
the screen width with the walls framing the lane. `PLAYER_Z` followed (−13..−2)
and `DESPAWN_Z` went to 9.

A second request took this much further — see 26 for the values that hold today.

### 19. Engagement band: no enemy fires from off-screen

Enemies spawn at `SPAWN_Z = -26`, well beyond the visible edge, so they can fly
in — but the weapon clock ran from spawn, so they fired from where the player
could not see them. `ENGAGE_Z_MIN/MAX` now defines the band in which an enemy
fights, and the clock **freezes** outside it (rather than merely blocking the
shot): if the timer kept running, a ship would enter the screen already charged
and fire with no telegraph, which is the opposite of what §7 asks. This applies
to the shared `tickWeapon` and also to `wraith` and `lance`, which have their own
clocks.

Locked down by test: a spy on `bullets.spawn` records the **origin** of every
enemy shot and fails if one is born outside the band. It has to be the origin and
not the current position — a shot aimed at the player by an enemy that has
already passed them travels legitimately far from the camera.

### 20. A cosmic backdrop in place of the ground

The ground became deep space: an fbm nebula plus three lattice star layers, each
scrolling at a different rate (it is the spread of rates that reads as depth).
The plateau that closed off the sides is gone — the canyon is now a pair of
structures suspended over the void, and past the wall you see stars. Each act's
tone still separates the biomes, because the nebula is tinted by the act's
`wallEdge`/`fog`.

**Careful when editing that shader:** it writes **linear** colour, and the effect
chain does the linear→sRGB encode on output. A middling value there comes out far
brighter than the source hex suggests — exactly the mistake the first attempt
made, which turned into a flat turquoise wash. That is why every coefficient is
so small, and there is a comment in the file saying so.

### 21. The logo overflowed the width on the boot screen

`SPACEROCKER` is a single ~8em word in Archivo Black. At
`font-size: clamp(48px, 13vw, 168px)` it measured 1330px inside a 1100px column —
at **every** width, including 420px. And because `main` only had
`overflow-y: auto`, the spec promotes `overflow-x` to `auto`: hence the horizontal
scrollbar and the text cut down to "spacer".

Two fixes: `main` declares `overflow-x: clip` explicitly, and the logo is sized in
`cqi` against its own column (`min(11.5cqi, 168px)`), the one unit that already
discounts the padding. Measured from 320px to 1920px: ~8% slack left over and
`scrollWidth === clientWidth` at every size.

## What the playtest found

`npm run playtest` runs the real simulation with a bot and no renderer — all 15
levels in seconds. `--run` plays the whole campaign carrying weapons. This is what
satisfied rule 5 of §16 ("test by playing"), and it found three bugs no unit test
would have caught.

### 22. All three bosses were immortal

The core was gated behind an **HP threshold** (`exposeAt: { core: N }`). But the
core's own HP counts toward the bar: destroying everything that is not the core
left the Hexapod at 39%, the Basilisk at 31% and the Ouroboros at 30% — none of
them reached the threshold that would open the core. A deadlock: the core only
opens with damage that only the core could take.

§8 never asked for that — it says "destroying a part ... opens access to the
core", and for the Hexapod it is explicit: "only exposed once the bay falls". The
gate is now per **destroyed part** (`coreExposedBy`), not per HP. The Hexapod
follows the spec's rule (the bay); Basilisk and Ouroboros open when the parts
guarding them fall.

For the Ouroboros the mode is `'any'`: §8 calls those things "core vents" — they
are the way in, not four locks. Requiring all four left the fight endless even
with the deadlock resolved.

Two new tests lock this down: one forbids an HP threshold on the core, the other
checks that the core alone sits below the first phase threshold.

### 23. 6000 of the Ouroboros's HP was out of reach

Anchors are a fraction of the hull frame's width, which at 2.6× is ~38 world
units. Cannons at `±0.34` landed at x=±12.9 and the arms at ±19.8 — but the lane
is only ±11.5. Six cannons and two arms were HP the player had no way to line a
shot up with. Anchors pulled inward, and a test now checks that every part with
HP fits inside the lane.

### 24. Weapons did not carry between levels

Advancing a level called `startRun`, which means "new game" and **zeroed score
and armament**. Every level restarted on the single shot, and late boss HP is
balanced for a player arriving with SPREAD. There is now `advanceLevel`, which
preserves both; `startRun` still resets, which is correct for a new game and for
"try again".

### Measured balance

Time to bring each boss down, with the player sitting on the target:

| Boss | single shot | SPREAD 5 | SPREAD 7 |
|---|---|---|---|
| Hexapod | 30s | 9s | 8s |
| Basilisk | 76s | 19s | 15s |
| Ouroboros | 214s | 45s | 33s |

The full campaign clears 14 of the 15 levels with the bot, most of them with 0–8
deaths. Level 15 is the exception: the bot dies faster than it kills. With
infinite lives it walks all five phases and falls in 338s even on the single
shot, so the fight is structurally sound — it is just very hard, which for the
game's climax is a design decision, not a bug. Noted here for whoever tunes
difficulty.

### 25. Audio clipping

Three causes stacked, all in the `SfxEngine` gain chain:

1. **Voice stealing silenced nothing.** On hitting the limit, the code removed
   the bookkeeping entry from the array and left the sound playing. The voice cap
   became fiction — far more than 20 sounds could be audible at once, summing
   until they clipped. Each voice now has its own `GainNode`, and stealing means
   ramping that gain to zero.
2. **There was no limiter.** Only a gentle compressor. The chain is now
   `voices → bus → compressor → limiter → soft clip → volume → output`.
3. **Volume sat before the compressor.** So raising the volume only pushed the
   compressor harder and changed the behaviour of the whole mix. It now sits
   after the limiter: the limiter guarantees a bounded signal and volume only
   scales it down.

Measured, not estimated: `SfxEngine` accepts an external context, so the worst
case can be rendered in an `OfflineAudioContext` and the samples counted. With 76
sounds fired on the same instant (bomb + explosions + firefight), the peak is
**-5.7 dBFS at default volume and -2.6 dBFS at maximum volume, zero clipped
samples**.

The music runs in Tone's context and the SFX in its own, so **nothing limits the
sum of the two at the device**. The music limiter went from -1 to -3 dBFS to
leave headroom for that sum.

### 26. Scale: camera much further back, an immense environment

Requested with references to classic shmups: tiny ships, lots of space, a huge
cosmic backdrop.

Only two numbers actually change the look, because a uniformly larger world is
visually identical to a more distant camera:

- **`CAM_DIST` 25 → 36** — goes from ~34 to ~49 units of visible width and from
  ~21 to ~30 of depth.
- **`PX_PER_UNIT` 49 → 62** — the sprite shrinks relative to the world.

Together they take the ship from 7.6% to **4.2% of the screen width**. The rest
follows: `TERRAIN_SCALE` widens the canyon by 1.45× (without touching the 15
level files), `BOSS_WORLD_SCALE` keeps the Hexapod at 47% of the screen and the
Ouroboros at 99%, and enemy, shot and scroll speeds all went up ~30% because
everything started crawling on the larger lane.

The backdrop gained fbm with *domain warping* — feeding the noise back into its
own coordinates is what turns smooth blobs into filaments and voids — plus two
clouds of different colour and a layer of bright foreground stars. The first
attempt used too low a frequency (barely one noise cell fit on screen) and came
out flat.

§3's reading rule was measured after the change, because an orange nebula in Act
III alongside orange enemy fire is exactly the risk: background median 23–30,
projectiles at 135–189, and under 2% of the frame bright enough to compete.

### 27. Clipping, second pass: one limiter for both

The first fix (25) limited the effects bus and measured -5.7 dBFS — but the audio
still clipped, because my "headroom by construction" reasoning was wrong: music
at -3 dBFS **summed** with SFX at -5.7 dBFS gives 1.23 in linear, above 1.0.
Limiting each source separately does not limit the sum.

The music now adopts `SfxEngine`'s `AudioContext` (via `Tone.setContext`) and
drains into the same `masterBus`, which carries the final limiter. A single
limiter sees the whole mix.

Reproduced and fixed by measurement: injecting a signal into the music bus
alongside the 76-effect burst, the peak was **1.046 with 27 clipped samples**. The
leak came from `oversample: '2x'` on the final soft clip — the resampling filters
ring above the curve. The final stage now uses `oversample: 'none'` and a 0.94
ceiling. After: **-0.6 dBFS, zero clipped samples**, even with the music at full
scale and volume at maximum.

If Tone refuses the shared context, it falls back to `toDestination()` and each
side limits on its own — worse, but functional.

### 28. The ship could not reach the cursor

The mouse mapped linearly to `±PLAY_HALF_W`, so a cursor at the screen edge only
took the ship to the edge of the **lane**. With the camera pulled back (26) the
screen shows ±24.5 units against a ±16.5 lane, and the ship sat permanently
behind the cursor.

The `Renderer` now projects the camera ray onto the flight plane (`y = SHIP_Y`)
and returns the real world position, so the mapping corrects itself for any
camera change — no magic constant. Following went from 0.3 to 0.55.

Measured by projecting the ship back to the screen: **0px of difference** from the
cursor anywhere inside the lane. This also exposed that a `PLAYER_Z_MAX` of -3
left the bottom quarter of the screen unreachable; it went to +3.

### 29. The favicon is generated from the ship, not an external asset

Request: "add a favicon to the project". The project's rule is that everything is
generated (§1), so the icon comes out of the same pipeline:
`spritegen/favicon.py` calls `render_frame` on the `player` at 512px, adds the
emissive on top the way the engine does, and crops to the art's own `getbbox()`.

The ship is a thin, tall arrowhead. Framed with a polite margin it became three
grey pixels in a tab, so: it fills 90% of the plate, gets a rounded plate of the
void (`#05060D`) to give it mass, and a tight magenta bloom (blur at 2.2% of the
side, alpha 0.55) to separate the silhouette from the background. A wide bloom
smeared the whole silhouette at 16px — hence the tight one.

It lands in `public/` rather than `public/sprites/`, because the browser asks for
the web root: `favicon.ico` with all four entries (16/32/48/64, 32bpp),
`favicon-32.png` for anyone who prefers PNG, and `apple-touch-icon.png` at 180px
**flattened** over the void (iOS composites onto its own background and
transparent corners would look dirty).

`npm run icons` regenerates them. Verified by serving the build: all three answer
200 with `image/x-icon` and `image/png`.

## Bugs found during verification (and fixed)

- **The ground never scrolled.** The shader used `position` (the plane's local
  coordinate); since the plane lies in its own XY, `vPos.z` was 0 at every vertex
  — the grid did not move and the depth fog never applied. It now uses world
  position. That was half the sense of speed.
- **Only one wall drew.** The two wall ribbons have opposite winding; one was
  discarded by backface culling. Materials are now `DoubleSide`.
- **Confusable silhouettes.** In §9's silhouette test, `miner`, `splitter` and
  `runner` were the same rounded blur at 60px. As the spec demands, the shape
  changed rather than the colour: `miner` gained legs, `splitter` gained a waist
  between its two modules, `runner` became a dart with concave sides (and its
  ghost echo dropped below the alpha threshold, because it was padding out its
  own silhouette).
- **The `bulwark`'s plate did not read as a shield.** It was a thin, detached
  crescent. Thickened and pushed against the hull — the enemy only dies from the
  sides, so that has to be obvious immediately.
- **The sprite scripts pointed at a file that never existed.** `npm run sprites`
  and `sprites:act1..3` called `tsx spritegen/build.ts` — a leftover from the
  original plan, before the generator became Python. Anyone running them got an
  error. They now call `python -m spritegen.build`, as the README already
  documented.
- **The Ouroboros's anchors sat outside the hull.** Cannons and arms floated in
  the void: anchors are a fraction of the hull's *frame width*, and the hull art
  only occupies ±0.47 of it.

## Known gaps

- **Audio is now measured, but only the SFX.** The effects bus peak is verified
  offline (see 25). The music still has no listening validation here, and the sum
  of the two at the device only has headroom by construction, not by measurement
  — the two contexts cannot be measured together without actually playing.

- **The live audio path was never validated with an active context.** In both
  headless and automated headed Chromium the `AudioContext` stays suspended —
  Playwright's synthetic gesture does not count as a user gesture, and the test
  machine has no audio device. `currentTime` stays frozen at 0 and sound never
  actually plays here.

  In that state an error appears per callback, and the stack shows it is
  **internal to Tone**: `TickSource.getTicksAtTime` ← `Clock._loop` ←
  `Context.emit`. Tone's global clock queries its own tick timeline at
  `currentTime - lookAhead`, which is negative while the context sits at zero,
  and no event exists there. It is not our code and cannot be intercepted from
  outside — it disappears once the context actually runs, which needs a real
  click.

  The defences that are ours are in place: a single transport owner (StrictMode
  mounts twice), waiting for the context to run before building anything, BPM only
  after `transport.start()`, edge-driven rather than per-frame gain automation,
  SFX scheduling nothing while the context is suspended, and Tone imported on
  demand inside the gesture (which also took 340KB out of the initial bundle).
  **A manual browser test with sound on is still missing.**
- **60 fps was never measured in §12's load scenario.** What runs here is
  SwiftShader (software GL), which gives ~15 fps in any scenario and says nothing
  about a real GPU. The `F3` overlay reports fps, draw calls and pool occupancy;
  draw calls sit at ~20, well under the budget of 60.
- **External stem support is half-finished.** `manifest.json` is read and the
  synthesis falls back correctly when the entry is `null` (which is §10's hard
  requirement: work 100% with no audio file). Actually playing `.ogg` stems, with
  BPM-aligned crossfades, was not implemented.
